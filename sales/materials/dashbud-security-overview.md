Dashbud: Security Overview 

**Date: October 6, 2026** 

**Draft for internal review**  

 

Data Architecture 

Dashbud is designed to strictly govern and minimize access to your data. 

* With a direct connection, Dashbud does not store or access your underlying data at all: all queries are a pass-through from your backend to the user-viewer. 

* Where data is ingested (file imports, APIs), your data is isolated, encrypted, and governed by strict access controls. 

In all cases, Dashbud's AI layer operates on metadata and business context – never on raw or queried data. 

Direct database connections (PostgreSQL, MySQL, SQL Server) 

Dashbud reads only metadata — table names, column names, data types, and relationships. Queries are generated by the AI and executed against your database; raw data is never transmitted to Dashbud's infrastructure or to any AI service. 

Storage of unique values/taxonomies 

The one exception is for permission-based storage of unique values of columns that represent a taxonomy. During Semantic Model configuration, Dashbud may ask to inspect the unique values of low-cardinality columns such as "type" or "status.” For example, unique values for a task\_type column might be: "open", "in-progress", "closed". Dashbud stores these values as column metadata so that the query agent can translate user requests accurately. Inspection happens only if permission is granted by the user. Semantic model configuration is a technical feature and may be restricted from non-technical end-users as part of data governance. 

For direct DB connections: 

* Row-level data is never stored or accessed; unique values of technical/dimensional fields may be stored in Semantic Model. 

* Query outputs are not stored, so Dashbud never stores any substantive client data. 

* Data is encrypted in transit (see below). 

File imports and APIs (CSV, Google Sheets, API output) 

Imported and API data are ingested into a managed PostgreSQL database within Dashbud's infrastructure. Imported data is isolated by strict enforcement of organization and workspace restrictions, and encrypted in transit and at rest with row-level security. 

AI and data separation 

Across all connection types, Dashbud's AI receives only structural metadata (schema, column types, relationships) and business context (semantic model definitions, business rules) to generate SQL queries. Low-cardinality taxonomy values may be shared with AI services only with explicit user confirmation. Row-level data and query output data are never sent to AI services. 

* Dashbud does not use customer data to train, fine-tune, or develop AI models 

* AI operates as a translation layer: business questions in, SQL queries out, grounded in metadata and business rules 

* All generated queries are auditable — users can see exactly what was executed 

Encryption 

* **In transit:** All connections use TLS/SSL encryption 

* **At rest:** Data stored in Dashbud's infrastructure (file imports, credentials, OAuth tokens) is encrypted at rest 

Authentication and Access Controls 

* User authentication via Auth0 (industry-standard identity platform) 

* Strict enforcement of organization boundaries and workspace (shared intra-org) boundaries. 

* Role-based access control at the organization and workspace level: owner, admin, user (can query), viewer (can read reports). 

* Unique user identification for all platform access 

* OAuth 2.0 for third-party integrations (e.g., APIs) — tokens encrypted at rest, scoped to minimum necessary permissions 

Data Governance 

Dashbud provides workspace-level controls that let administrators determine what data each user or team can access before any query is run. 

* **Column exclusion:** Sensitive columns (e.g., SSN, date of birth, salary) can be excluded from a workspace entirely. Excluded columns are invisible to users and to the AI — they cannot be queried, filtered on, or referenced in reports. 

* **Row-level filtering:** Workspaces can be configured with row-level access rules that restrict queries to a defined subset of data. For example, a workspace for Department ABC can be filtered so that users only see rows where department \= "ABC." The filter is enforced at the query level: users cannot override or bypass it. 

* **Workspace scoping:** Administrators model the data once, then create scoped workspaces for different teams, roles, or use cases. Each workspace inherits the shared semantic model but enforces its own column and row restrictions. This allows a single data source to serve multiple audiences with appropriate access boundaries. 

 

These controls apply to both the conversational query interface and any reports or dashboards created within the workspace. The AI operates within the same restrictions – it can only generate queries against the data the user is permitted to see. 

Usage and Access Logging 

* Dashbud maintains logs of user activity and data access 

* Query execution is logged and traceable 

Infrastructure 

* Hosted on AWS (US-East) 

* Production and staging environments are fully isolated 

* No direct access to user data from any user role (admins cannot query backend directly) 

* Application served via AWS CloudFront with edge security 

Organizational Practices 

* Access to customer data and metadata is restricted to authorized personnel for support and diagnostics only 

* No customer data is shared with third parties unless explicitly authorized by the customer 

Compliance Posture 

* **HIPAA:** Dashbud is designed to support HIPAA-covered workflows. We offer our own Business Associate Agreement (BAA) or alternatively can sign the BAA of a customer handling protected health information. 

* **Privacy by architecture:** The schema-only AI model means sensitive data is not exposed to AI services by default, reducing compliance surface area 

* **Data ownership:** Customers retain all rights to their data. Dashbud acquires no ownership interest in customer data. 

* **Data portability:** Customers may request a complete export of ingested (import, API) data at any time 

* **Data deletion:** Customer data is deleted or returned upon termination, per agreement terms 

Self-Hosted Deployment 

For organizations with strict data residency or security requirements, Dashbud can be deployed directly into your own cloud environment. In this model: 

* The entire Dashbud platform — application, database, and all supporting services — runs within your cloud account (e.g., Azure, AWS) 

* **Your data never leaves your infrastructure.** Even ingested file data stays in a PostgreSQL instance you control 

* Dashbud's team manages the application; your IT team retains full visibility and control over the environment, network policies, and data 

* Eliminates third-party data custody concerns entirely — there is no Dashbud-hosted copy of your data 

This option is ideal for regulated industries (healthcare, social services, financial services) where data sovereignty is a compliance requirement or organizational policy.
